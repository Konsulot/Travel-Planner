## Замечания по запуску

- **Ошибки 429.** Бесплатная модель `xingchen-agi/xing4.0-29b-a4b:free` почти на каждый запрос отвечала `429 Provider returned error` (провайдер перегружен). Исходный `call_model` повторял запрос только при пустом ответе, а на исключение 429 сразу сдавался. Поэтому в `call_model` добавлен перехват `RateLimitError` и `InternalServerError` с повтором через 10, 20, 30, 40 секунд. Шаг 1 удалось пройти на ней с повторами, но на шаге 2 все 4 попытки закончились 429. Начиная с шага 2 использовалась `nvidia/nemotron-3-ultra-550b-a55b:free` (на ней делалась лаб. 2).
- **Лишние вызовы инструментов.** На простое «Меня зовут Иван…» модель начинала вызывать `list_files`, `search_docs`, `read_file`, хотя это не нужно. В `SYSTEM_PROMPT` добавлено: *«Если сообщение не требует работы с файлами, документацией или бюджетом (знакомство, вопрос о том, что говорилось раньше), отвечай сразу, без инструментов»*. После этого на знакомство модель отвечает без инструментов.

## Шаг 1. Сессия на диске

**Как устроено.**
- `python agent.py --session lab3` (или переменная `SESSION_ID`). Без `--session` создаётся новая сессия с id по дате и времени, и агент печатает команду, как её продолжить.
- `save_session(id, messages)` пишет `sessions/<id>.json`: id, модель, время, `messages[1:]`. Сохраняет **после вопроса пользователя, после каждого шага агента** (колбэк `on_step` в `run_agent`) и после финального ответа. Запись идёт через временный файл и `replace()`, поэтому падение во время записи не портит сессию.
- **Системный промпт в файл не пишется.** `load_session` всегда ставит первым актуальный `SYSTEM_PROMPT` из кода, поэтому он не дублируется при каждой загрузке и подхватывает правки промпта.
- **Секретов в файле нет:** ключ из `.env` хранится только в объекте `client` и в `messages` не попадает.
- `repair_history` при загрузке выбрасывает незавершённый tool-цикл. Если программу закрыли посреди шага, в файле мог остаться `assistant` с `tool_calls` без ответов `role: tool`, и API отклонил бы такую историю.
- `session_file` пропускает только id из `[A-Za-z0-9_-]`, чтобы через `--session ../../x` нельзя было писать за пределы `sessions/`.

**Результат.** За одну задачу вход вырос почти вдвое: `prompt_tokens` с 1458 до 2732, оценка с 992 до 1563. Сильнее всего его увеличивают результаты `search_docs` (+479 и +357 `prompt_tokens`), короткие ответы `set_budget`/`add_expense` добавляют по 100–200.

**Почему растёт.** Модель не хранит состояние, поэтому каждый запрос содержит всю историю: system, `TOOLS`, вопросы, ответы ассистента с `tool_calls` и результаты инструментов. После `read_file`/`search_docs` вход прыгает сильнее всего: текст документа остаётся в истории и повторно отправляется на каждом следующем шаге.

**Почему оценка не совпадает с `prompt_tokens`.** Оценка занижена в 1.5–1.75 раза (отношение 0.68 → 0.57), и разрыв растёт с каждым шагом:
1. Правило «4 символа = 1 токен» выведено для английского текста, а кириллица токенизируется плотнее (меньше символов на токен).
2. API добавляет служебные токены на разметку ролей и схему инструментов.
3. Главная причина роста разрыва: nemotron — reasoning-модель. Её ответ сохраняется в историю целиком (`msg.model_dump()`), вместе с полями рассуждений, и отправляется обратно. API эти токены считает, а `estimate_tokens` учитывает только `content` и `tool_calls`. Чем больше ответов ассистента в истории, тем больше неучтённых рассуждений.

Для бюджета это допустимо: важна не точность, а то, что оценка растёт вместе с фактом. Но бюджет надо ставить с запасом: при `CONTEXT_BUDGET=6000` реальный вход может доходить примерно до 9–10 тыс. токенов.

## Шаг 3. Бюджет и усечение

**Как устроено.** `CONTEXT_BUDGET` — бюджет в условных токенах оценки. `ensure_context_budget(messages)` вызывается **перед каждым запросом к API**:

1. `split_turns` делит историю на «голову» (system + `[память диалога]`, если есть) и **ходы**. Ход = сообщение `user` + все `assistant`/`tool` после него.
2. Пока оценка больше бюджета и ходов больше одного, удаляется **самый старый ход целиком**. Пары `tool_calls` → `role: tool` никогда не разрываются, поэтому «осиротевших» `tool` не бывает. System и текущий ход (последний вопрос со всем его tool-циклом) сохраняются всегда.
3. Если текущий ход сам больше бюджета (например, агент прочитал несколько больших файлов), `shorten_tool_results` сокращает **старые** результаты инструментов этого хода до 400 символов с пометкой `…[сокращено, было N символов]`. Результаты после последнего ответа ассистента не трогаются: модель их ещё не видела.
4. Если сокращать больше нечего, агент пишет `WARN` и всё равно отправляет запрос. Программа из-за обрезки не падает.

В лог пишется `TRIM: removed N старых сообщений; ≈до → ≈после ток.`

## Шаг 4. Суммаризация старого хвоста

**Как устроено.** При `STRATEGY=summarize` удаляемые ходы не выбрасываются, а сжимаются:

- `render_for_summary` превращает их в простой текст: реплики, вызовы инструментов, обрезанные результаты.
- `summarize_messages` делает **отдельный короткий запрос к модели без `tools`** (`call_model(..., use_tools=False)`) с промптом «сожми в заметку: Пользователя зовут… Цель… Ранее сделано… Важные факты и числа… Открытые задачи…». Если память уже была, старая память объединяется с новым фрагментом.
- Результат кладётся **сразу после system** как `{"role": "system", "content": "[память диалога] …"}` вместо удалённого хвоста и сохраняется в сессию.
- Под память резервируется `SUMMARY_RESERVE = 300` токенов бюджета, длина ограничена 1200 символами.
- **Fallback:** если запрос упал или модель вернула пустой текст (у reasoning-модели всё может уйти в рассуждения), печатается `SUMMARY: не получилось — fallback на TRIM` и работает обычное усечение.

## Шаг 5. Инструмент `search_docs`

**Как устроено.**
- Параметры: `query` (обязательный), `limit` — целое 1–5, по умолчанию 3.
- Ищет **только в `workspace/docs/`**: путь получается через `safe_path("docs")`, а каждый файл дополнительно проверяется `is_relative_to(docs)`, чтобы симлинк не вывел наружу. Читаются только `.md` и `.txt`.
- Документы делятся на абзацы (по пустой строке), у каждого запоминается заголовок раздела.
- Запрос → слова в нижнем регистре → стоп-слова («как», «что», «найди»…) выбрасываются → простой стемминг `stem()`: отрезаем окончание, оставляем до 6 букв основы. «бюджет» находит «бюджета», «обновляются» находит «обновляет».
- **Score:** за каждое найденное слово запроса `idf × (1 + 0.5, если слово в заголовке) + 0.1 за повторы`. `idf = ln((N+1)/(df+1)) + 1` — вес редкости: «бюджет» есть почти везде и весит мало, «демо» редкое и весит много. Без idf длинные абзацы с частыми словами вытесняли нужный ответ.
- Ответ короткий: `[путь › раздел] (score)` и фрагмент до 400 символов, максимум `limit` штук.
- Ошибки строкой: `ОШИБКА: пустой запрос…`, `ОШИБКА: limit должен быть от 1 до 5`, `ОШИБКА: папка workspace/docs не найдена`. Если ничего не найдено, возвращается обычный ответ «ничего не найдено», а не ошибка.

## Итоги

- **Краткосрочная память между запусками:** история в `sessions/<id>.json`.
- **Контекст не растёт бесконтрольно:** перед каждым запросом оценка сравнивается с `CONTEXT_BUDGET`, старые ходы удаляются целиком или сжимаются в `[память диалога]`, история остаётся валидной для API.
- **Знания о проекте:** агент не читает все документы целиком, а находит нужный абзац через `search_docs`. Это ещё и экономия контекста по сравнению с `read_file`.
